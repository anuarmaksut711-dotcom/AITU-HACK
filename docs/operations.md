# Запуск и эксплуатация первого слоя

## Локальный запуск

Требуется Docker Engine / Docker Desktop с Compose v2 и Python 3 для генерации локальных секретов. Сборке нужен доступ к реестрам пакетов и образов. Для runtime моделей пока не требуется.

```sh
make up
```

Команда создаёт `.env` с правами `0600`, собирает образы, ждёт healthchecks, применяет миграции и запускает bootstrap пользователя. Существующий `.env` не перезаписывается. Адрес: http://127.0.0.1:8787. Email и пароль находятся в локальном `.env` как `BOOTSTRAP_EMAIL` и `BOOTSTRAP_PASSWORD`. Не помещайте этот файл в Git.

Для другого порта поменяйте `WEB_PORT` и оба адреса `ALLOWED_ORIGINS`. `localhost` и `127.0.0.1` — разные браузерные origin и отдельные cookie-контексты; используйте один адрес последовательно.

```sh
docker compose ps
docker compose logs --tail=100 api web migrate
curl --fail http://127.0.0.1:8787/api/health/ready
```

`/api/health/live` показывает работоспособность API, `/api/health/ready` дополнительно проверяет соединение с БД. Состояние healthcheck не доказывает работу AI: в этом слое его нет.

### Разработка фронтенда через Vite

При запущенном Compose:

```sh
cd apps/web
npm run dev
```

Откройте http://127.0.0.1:5173. Vite направляет `/api` через Aimeet web на `http://127.0.0.1:8787`: порт API `8000` находится внутри Docker-сети, а на хосте может принадлежать другому проекту. Для запросов с origin самого локального Vite-сервера прокси передаёт origin целевого Aimeet web, чтобы работали вход и сохранение; посторонние origin остаются без изменений для проверки API.

Если изменён `WEB_PORT` или используется отдельно запущенный API, укажите его адрес при запуске. Целевой origin должен входить в `ALLOWED_ORIGINS` API:

```sh
AIMEET_API_TARGET=http://127.0.0.1:8788 npm run dev
```

## Остановка и обновление

`make down` останавливает сервисы и сохраняет PostgreSQL volume. Не используйте `docker compose down -v`, если хотите сохранить данные. Перед обновлением создайте резервную копию. Миграция запускается как отдельный one-shot сервис; API ждёт её успешного завершения. Запуск двух установок требует отдельного Compose project name, порта и томов.

## Резервная копия

```sh
make backup
```

Создаёт `backups/aimeet-<UTC>.dump` в формате PostgreSQL custom с правами `0600`. Текст встреч и учётные записи входят в копию; храните её как конфиденциальные данные. Папка исключена из Git. Скрипт не настраивает расписание или внешнее хранение.

Автоматическая проверка выполняет восстановление в отдельную временную БД и удаляет только её после проверки:

```sh
python3 scripts/verify-backup.py backups/ИМЯ_КОПИИ.dump
```

Ручной вариант:

```sh
docker compose exec -T postgres createdb -U aimeet aimeet_restore_check
docker compose exec -T postgres pg_restore -U aimeet -d aimeet_restore_check --no-owner < backups/ИМЯ_КОПИИ.dump
docker compose exec -T postgres psql -U aimeet -d aimeet_restore_check -c '\dt'
```

Проверьте записи в восстановленной БД прежде чем направлять на неё приложение. Не восстанавливайте копию поверх рабочей БД без отдельной процедуры переключения и подтверждённого отката.

## Размещение за HTTPS

Текущий Compose предназначен для одной локальной установки и слушает только loopback. Для реального сервера нужен TLS reverse proxy перед web. Задайте `APP_ENV=production`, `COOKIE_SECURE=true` и точный HTTPS origin. Backend должен отказываться стартовать в production с небезопасной cookie. Не открывайте PostgreSQL и API напрямую и не передавайте браузеру секреты.

Отдельные ворота перед внешним размещением: TLS и заголовки прокси, управление пользователями/восстановление доступа, срок хранения записей, квоты и нагрузка, резервное копирование с восстановлением, аудит зависимостей и процедура обновления закреплённых Docker-образов. Это требования будущей эксплуатационной приёмки, а не подтверждённые возможности первого слоя.

## Проверки

Frontend: `cd apps/web && npm ci && npm run lint && npm run build`.

Backend: `cd apps/api && uv sync --frozen --group dev && uv run ruff check . && uv run pytest`.

Интеграционные тесты запускаются с отдельной `TEST_DATABASE_URL`, **никогда** с рабочей БД. Browser E2E использует `E2E_EMAIL`, `E2E_PASSWORD` и запущенную локальную установку. Тестовые встречи должны удаляться тестом.
