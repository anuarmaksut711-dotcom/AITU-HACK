# Локальное распознавание аудио

## Выбор движка

Для сценария ТЗ «загрузить MP3/WAV/M4A → получить стенограмму локально» используется **Faster-Whisper 1.2.1**. Сравнение проверено 11 сентября 2026:

| Вариант | Когда уместен | Решение для Aimeet |
| --- | --- | --- |
| [Vexa](https://docs.vexa.ai/) | Боты для Meet/Teams/Zoom, захват и потоковая транскрибация; есть self-hosted вариант | Оставить будущим источником записей. Для загрузки файлов добавляет ненужную инфраструктуру ботов; облачный API не соответствует offline-сценарию ТЗ |
| [Faster-Whisper](https://github.com/SYSTRAN/faster-whisper) | Python, локальные модели, CPU INT8 / NVIDIA CUDA, VAD и сегменты с временем | Реализован в отдельном worker существующего приложения |
| [whisper.cpp](https://github.com/ggml-org/whisper.cpp) | Нативное приложение, особенно Apple Silicon с Metal/Core ML | Возможный следующий адаптер для нативного Mac. Текущий Docker worker использует CPU |
| [Sherpa-ONNX](https://k2-fsa.github.io/sherpa/onnx/speaker-diarization/index.html) | Локальная сегментация голосов и кластеризация участников на CPU | Подключён к Faster-Whisper: pyannote segmentation 3.0 ONNX + NeMo TitaNet small, слова привязываются к голосам по времени |

Это выбор по сценарию и существующему стеку, а не результат сравнительного теста качества всех движков. Vexa self-hosted с собственным STT может сохранять данные внутри инфраструктуры; подключение к онлайн-встрече при этом требует сети.

## Подготовка и запуск

Из корня проекта, один раз с интернетом для установки пакетов и весов:

```sh
uv sync --project apps/api --group dev
uv run --project apps/api python scripts/prepare-stt-model.py
python scripts/prepare-diarization-models.py
make up
```

Модель скачивается в `models/whisper-large-v3-turbo`. Скрипт сначала получает commit SHA, скачивает именно эту ревизию в `.partial`, проверяет обязательные файлы и атомарно публикует каталог. `aimeet-model.json` содержит репозиторий и ревизию. Существующий каталог не перезаписывается. Для переноса в изолированную среду достаточно перенести целиком `models/whisper-large-v3-turbo`, собранные Docker-образы и приложение. Модель и записи исключены из Git и Docker build context.

В интерфейсе: **Встречи → Загрузить аудио → выбрать файл → Распознать запись**. Название подставляется из имени файла; перед загрузкой его и язык можно изменить. Ручной ввод стенограммы убран из формы создания, существующие текстовые встречи остаются доступны.

После загрузки открывается экран с вкладками «Разговор» и «Итоги». Распознаватель передаёт сегменты сразу после их получения; worker сохраняет промежуточный текст и временные отметки не чаще одного раза в две секунды, а клиент обновляет запись каждые 1,5 секунды. Это реальные промежуточные результаты, а не воспроизведение готовой стенограммы. Автопрокрутка приостанавливается, если пользователь прокрутил разговор вверх.

Финальная стенограмма и задание на подготовку итогов сохраняются в одной транзакции. Анализ запускается автоматически даже при закрытой странице. Проверенные по цитатам промежуточные выжимки видны во время анализа; карточки публикуются после согласования выводов по всей записи. Для этого должен работать `intelligence-worker`. Ошибки распознавания и анализа показываются отдельно, с возможностью повторить соответствующий этап.

Промежуточная стенограмма остаётся черновиком и не участвует в поиске по встречам. При отмене уже распознанные фрагменты сохраняются; повторный запуск очищает их. Запись промежуточных результатов защищена тем же сроком владения заданием, что и финальная публикация.

Ограничения: 100 МиБ на файл, 2 часа декодированного аудио, 200 000 символов результата. Название «100 МБ» в интерфейсе соответствует 104 857 600 байтам. Речь распознаётся в исходных языках, без задания перевода на английский. Включён `multilingual=True`: Faster-Whisper повторно определяет язык в каждом окне декодирования, а не фиксирует его на всю запись. Для смешанной қазақша / русский / English речи выбирайте «Авто». Явно выбранный язык служит начальной подсказкой; переключение языков остаётся включённым. В живых комнатах действует тот же режим, новые комнаты создаются с `auto`. Это не детектор языка каждого слова: короткие вставки, имена и переключения внутри одного окна всё ещё могут распознаваться с ошибками. Для такого сценария по умолчанию используется мультиязычная large-v3-turbo; точность требует проверки на настоящей смешанной речи.

## Участники разговора

Для загружаемых файлов диаризация включена по умолчанию. Сначала Sherpa-ONNX анализирует всю запись и группирует голоса, затем Whisper распознаёт слова с временными отметками. Один фрагмент Whisper может разделиться на несколько реплик, если внутри него меняется говорящий. Подписи «Участник 1», «Участник 2» выдаются по первому появлению голоса и сохраняются при его возвращении. Имена и роли людей по голосу не определяются. При неуверенном пересечении голосов или отсутствии совпадения по времени подпись остаётся пустой.

Поле `segments[].speaker` передаётся через API и показывается рядом со временем. Подпись также входит в исходный `text` сегмента и общую стенограмму — как в архиве Live — поэтому итоги, цитаты и поиск сохраняют контекст говорящего. Интерфейс выводит эту подпись один раз в заголовке реплики. Старые стенограммы без `speaker` продолжают читаться; для получения голосов их нужно загрузить повторно. Уже сохранённый текст и итоги автоматически не переписываются.

Модели находятся в `models/speaker-diarization` и монтируются в worker только для чтения. Установщик сохраняет URL и SHA-256 скачанных файлов; записи пользователей он не читает. В рабочем процессе скачиваний нет. Для переноса offline-установки скопируйте этот каталог вместе с моделью Whisper. При отсутствии моделей возвращается `diarization_model_missing`, при ошибке их запуска — `diarization_failed`.

Настройки: `STT_DIARIZATION_ENABLED=true`, `STT_DIARIZATION_MODEL_DIR=speaker-diarization`, `STT_DIARIZATION_THRESHOLD=0.9`. Число голосов определяется автоматически; увеличение порога объединяет больше голосов, уменьшение разделяет их сильнее. Порог не заменяет проверку качества. При известном числе участников в форме загрузки можно указать от 1 до 32; API принимает `num_speakers`. Ограничение сохраняется в задании и при повторе обработки. По умолчанию остаётся авто, а не фиксированные два человека. `STT_DIARIZATION_ENABLED=false` явно возвращает режим распознавания без определения участников. В живых комнатах участники определяются по отдельным аудиопотокам подключения; несколько людей у одного микрофона в реальном времени пока не разделяются.

После уточнения пользователя о двух людях в EXPO проверена чувствительность авто. Исходный порог 0.5 давал 5 групп в EXPO и 8 в [контрольной записи Sherpa с четырьмя говорящими](https://github.com/k2-fsa/sherpa-onnx/releases/download/speaker-segmentation-models/0-four-speakers-zh.wav). Порог 0.9 даёт соответственно 3 и 4; в EXPO третья группа занимает только 13.70–16.28 с. Пороги 1.0/1.1 дают 2 группы в EXPO, но ошибочно объединяют контрольных участников до 3/2, поэтому глобально не применяются. Альтернативный CAMPPlus zh/en тоже не устранил спорную группу. Новый порог уменьшает дробление, но точная идентификация двух участников в авто пока не подтверждена. `num_speakers=2` ограничивает кластеризацию двумя голосами; это не доказательство правильности каждой реплики.

Проверка ограничения: `smoke-transcription.py --num-speakers 2 --min-speakers 2` прошёл весь путь загрузка → worker → API на EXPO и вернул две группы (178,25 с при параллельной нагрузке). Валидация диапазона 1–32 и сохранение выбора при повторе покрыты API-тестом; браузерный тест проверяет передачу выбранного числа в запросе загрузки. 22 профильных API-теста прошли, PostgreSQL-only тест пропущен; проверка POSIX-прав файла исключена на Windows.

Диаризация занимает начальную часть прогресса (до 25%), затем реплики публикуются по мере распознавания. В Docker настроена загрузка ONNX Runtime для Sherpa; этот образ — поддерживаемый путь запуска на Linux. Для локального Python на Windows адаптер загружает DLL из установленного пакета ONNX Runtime, чтобы не использовать устаревшую системную DLL.

Linux wheel Sherpa 1.13.8 требует точную ABI-версию `VERS_1.28.2`. При сборке образа `infra/docker/install-sherpa-runtime.py` устанавливает [соответствующую сборку ONNX Runtime от сопровождающего Sherpa](https://github.com/csukuangfj/onnxruntime-libs/releases/tag/v1.28.2) с проверкой закреплённого SHA-256 для x86_64/aarch64. Это отдельная библиотека от Python-пакета ONNX Runtime для Whisper/VAD; простой симлинк на более новую Python-библиотеку несовместим.

По умолчанию `large-v3-turbo`, CPU INT8, четыре потока, лимит контейнера 4 ГБ и 4 CPU. Это стартовая настройка для ноутбука. Для проверки более крупной мультиязычной модели:

```sh
uv run --project apps/api python scripts/prepare-stt-model.py --model large-v3-turbo
# В .env: STT_MODEL_DIR=whisper-large-v3-turbo
# При необходимости увеличить STT_MEMORY_LIMIT; затем:
docker compose up -d --no-deps transcription-worker
```

Смена модели не меняет уже готовые стенограммы. Наличие поддержки казахского языка не доказывает достаточное качество на казахской или смешанной речи. Нужен отдельный корпус реальных встреч с проверкой имён, чисел, терминов, тишины, шума и пересечений голосов. NVIDIA CUDA поддерживается адаптером, но стандартный Compose CPU-only: GPU требует отдельного образа с CUDA/cuDNN и настройки устройства. Metal из Docker здесь не используется.

## Жизненный цикл

- `POST /api/v1/meetings/audio` принимает поток байтов `application/octet-stream`; `title`, `filename`, `language` задаются query-параметрами. Веб-прокси не буферизует целиком аудио. API требует сессию и CSRF-проверку до чтения потока.
- Запись сохраняется с правами 0600 под UUID, оригинальное имя служит только метаданными. Размер считается по реально прочитанным байтам. SHA-256 проверяется перед распознаванием.
- Запись и задание фиксируются в одной транзакции после сохранения файла. При ошибке транзакции файл удаляется. При обычном обрыве загрузки временный файл удаляется.
- PostgreSQL выдаёт задание через блокировку строки `SKIP LOCKED`. Worker продлевает аренду каждые 2 секунды. После его падения задание становится доступно примерно через 60 секунд; максимум три автоматические попытки восстановления.
- Каждая попытка получает уникальный токен. Отменённый/удалённый или потерявший аренду процесс не может опубликовать результат. Успех, текст и сегменты сохраняются атомарно.
- Декодирование, VAD и модель работают в дочернем процессе. Worker завершает его при отмене, потере аренды или таймауте 4 часа. У контейнера есть ограничения памяти, CPU и числа процессов.
- Транскрипция использует только локальные файлы (`local_files_only=True`, offline-переменные, отключённая телеметрия ONNX). У transcription-worker только внутренняя сеть `data`; каталог модели и аудио смонтированы только для чтения. Загрузка модели происходит отдельной установочной командой.
- Ошибки декодирования, отсутствующая модель и отсутствие речи дают явное состояние ошибки; фиктивный текст не подставляется. Текст и содержимое исключений не попадают в логи worker.

Полная локальность других подсистем, включая отдельно разрабатываемый RAG, зависит от их конфигурации. Эта реализация гарантирует отсутствие облачного ASR в пути распознавания, не сертифицирует весь продукт как offline.

## Хранение и резервная копия

PostgreSQL содержит метаданные, задания и стенограммы; исходное аудио находится в Docker-томе `audio-data`. Удаление встречи отменяет её задание, удаляет данные из БД и файл. Старые копии в backup управляются отдельно.

`make backup` сохраняет только БД. Для полной копии аудиовстреч нужно также сохранить `audio-data` на той же точке остановки. Пример для локального обслуживания:

```sh
docker compose stop api transcription-worker
make backup
docker compose run --rm --no-deps --entrypoint tar api -C /data/audio -cf - . > backups/audio.tar
docker compose start api transcription-worker
chmod 600 backups/audio.tar
```

При восстановлении нужны оба артефакта и права владельца тома 10001:10001. Не восстанавливайте поверх рабочей БД без проверки. При аварийном завершении API между записью файла и commit может остаться файл без записи в БД; периодическая сборка таких файлов и общие пользовательские квоты пока не реализованы. Ручная очистка допустима только после сверки UUID с `meetings`, с остановленной загрузкой. Миграция 0002 не предлагает разрушительный автоматический downgrade: откат выполняется из резервной копии.

## Проверки

Проверка добавления диаризации 11.09.2026: 184 backend-теста прошли в Linux-контейнере, 3 PostgreSQL-only теста пропущены. Две браузерные проверки прошли в Chrome: подписи участников и смешанный текст на desktop/mobile, создание комнаты с автоматическим языком. TypeScript и lint проверены. Старый E2E `audio upload shows progressive results and keeps the sidebar on the left` доходит до вкладки итогов, но падает на ожидании `summary`: fixture отдаёт `cards: []`, тогда как уже существовавший экран отображает карточки. Это отдельное расхождение старого теста, не проверка точности ASR.

Реальный `EXPO 2017 Astana 2.m4a` (171,028 секунды) прошёл загрузку → отдельный worker → API → удаление в изолированной SQLite БД: на Windows 145,05 секунды, в Docker с `--network none`, read-only root, 4 CPU и 4 ГБ — 171,81 секунды. В обоих прогонах кластеризация выдала 5 групп голосов. Это проверка работоспособности, не подтверждённое эталонной разметкой число участников или оценка точности смешанной речи. Рабочие записи не изменялись.
